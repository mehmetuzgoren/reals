# Privacy and publication model

## One authority for content

`convex/lib/access.ts` is shared by original reads, reply reads/counts, caption reads, grant issuance, each HTTP grant redemption and direct-reply notification eligibility. An original is owner-readable for history. Other viewers need the current round, a successful receipt in that exact round and an approved, unblocked friendship with its author. A pending request is never a friendship. A reply first passes its parent; A↔B must still be approved/unblocked, and a third viewer must be approved/unblocked friends with both A and B. Reply ownership permits deletion, not access to a hidden parent. Each response is built from viewer-visible records rather than returning raw database rows.

Casey (friends with Alex and Blair) can see Blair's reply on Alex's original after posting. Dana (only friends with Alex) sees Alex's original with zero visible replies and cannot redeem or obtain either asset of Blair's reply, read its caption or report it. Removing A↔B hides the exchange from normal playback for everyone. New-round opening relocks friends' content, including existing grants, while owners retain their own historical originals.

## Actual bytes before atomic success

An authenticated expiring upload intent is unique per owner/request ID. A short lease prevents concurrent/replacement uploads. The HTTP route authorizes before reading a bounded body, hashes and stores those actual bytes, and binds the storage ID through an internal mutation. Public clients cannot assert a storage ID, duration, owner or verification result. A storage object whose binding loses a race is deleted; an aged-orphan sweep catches a process death between store and bind.

Finalization leases work, reads that bound object, verifies its hash, and sends those bytes to the included authenticated decoder service. Missing/failed processing never unlocks. The final mutation checks the lease, expiry, verified hash/metadata, current round, valid option, receipt uniqueness and relationship/parent access **again**, then writes exactly one immutable original+receipt or one reply and the idempotent upload result. Concurrent attempts conflict/retry under Convex serializable transactions. Retryable verifier failures retain staging until expiry; a lost processing lease can be reclaimed. Client cancellation/deletion wins against stale processing. Terminal failures have no receipt.

Original deletion immediately hides its conversation, clears the receipt's original reference and schedules dependent reply/media/report cleanup. The receipt success fact persists and still unlocks the exact round while preventing republishing. Successful upload-result records persist for idempotency until account deletion. An old result is not authorization to read content that has since been deleted, blocked or relocked.

## Grant and avatar boundaries

Private URLs contain 256-bit random grant tokens; only SHA-256 hashes are stored. Each grant binds viewer/content/kind/asset and expires after 60 seconds. GET/HEAD re-evaluates active user and shared access; Range is checked only after authorization. There is no raw storage resolver, reusable private storage URL or redirect. Bodies and captions do not appear in locked envelopes. Responses are `private, no-store`, with no sniffing or referrer disclosure. A token URL is still a short-lived bearer capability: do not log it, and a recipient can retain bytes already received.

Minimal avatars are a distinct public-profile choice. Raw image uploads are owner-private and are decoded/normalized by the verifier before profile binding. Their sanitized JPEG route serves only the active user's selected avatar, never an arbitrary storage object. Changing/deleting an avatar cleans the superseded asset. A leaked avatar URL cannot resolve video, thumbnails, captions, staging or user tokens.

## Bounded MVP policy

Video intent/body cap is **8 MiB**, not an assumed 20 MiB multipart limit. Native should export a <=15-second portrait H.264/AAC MP4 at a bitrate that fits the returned cap (720p at about 3 Mbit/s is normally under 6 MiB; measure actual output). The included worker has a separate hard ceiling of 20 MiB, so direct oversized service callers cannot disable bounds. HTTP raw bodies are counted independently of `Content-Length`. The 8 MiB app cap leaves headroom for body/hash/blob copies inside Convex's 64 MiB HTTP/action runtime; private response bodies are no larger than the original or <=512 KiB JPEG. Convex's current documented HTTP response ceiling is 100 MiB, not a reason to accept or buffer larger uploads. Verify memory/bandwidth under load before increasing the cap.

Intents last ten minutes; upload/processing leases last two minutes; verifier calls time out after 45 seconds. Expired staging/grants are swept every ten minutes in bounded batches. Unbound stored objects older than one hour are swept every twelve hours using indexed references; this preserves recent in-flight stores and published assets. Original cleanup hides immediately and removes dependent rows/assets in batches; account tombstones revoke authorization before asynchronous cleanup.

An account may have three active video intents, three active avatar intents, 200 approved friends, 100 outgoing/200 incoming pending requests, 500 own blocks, ten devices, 200 live media grants and 100 active reports. Conversations accept at most 50 stored replies; feed pages cap at eight originals, history at ten, replies at 50. These are explicit MVP safety bounds, including a serializable limit check at finalization. A deleted reply can free a reply slot; published originals and successful receipts remain immutable. Request-local authorization memoization keeps count/read queries within Convex transaction/index-range budgets without carrying authorization across requests. Do not remove the bounds or cache access globally without a new load/privacy review.

Convex operations/bytes, stored clips, verifier CPU, outbound verifier copies, private playback and FCM traffic incur service costs. Range/HEAD and lazy AVPlayer loading avoid eager downloads, but every authorized media request still rechecks the database and uses Convex bandwidth; there is deliberately no CDN cache. Live deployments require authenticated-ingress quotas/rate controls and monitoring. Application limits are not a substitute for provider-level abuse protection, a privacy retention policy, or real load testing.

## Verification scope

The automated Convex tests exercise identity/profile/social/publication/account functions and real registered HTTP routes with transaction limits, including locked direct IDs/media, the Casey/Dana matrix, visible counts, both media assets, revocation, failed processing, concurrency, exact-round unlock, preserved receipts, new-round relock, Range/HEAD and cleanup. Their mocked verifier proves orchestration, not decoding. The worker tests exercise actual FFprobe/FFmpeg fixtures and HTTP authentication/bounds; remote Firebase token acceptance, real APNs delivery, Convex cloud resources and physical capture remain external launch checks. No unavailable transcription is advertised as `ready`.
